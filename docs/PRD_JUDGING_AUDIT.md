# GiftGuard: original PRD and judging audit

GiftGuard fits the challenge when it remains a simple weekly routine: bring in the files, review possible duplicates, and contact the people whose regular gifts appear late. The strongest evidence is a preserved donor history and a useful follow-up list. Voice and visible agent activity help Denise perform that work; they should not displace it in the interface or demonstration.

This audit compares the original supplied PRD and judging map with the current source, tests and verification record. The latest recorded baseline before this audit is **117 passing tests**, with TypeScript, lint and production build passing. This audit is a source review, not a fresh execution of those checks. The parent agent also checked local package resolution during this audit and confirmed that `@openai/agents` remains unavailable. Browser rendering, a real microphone conversation, live OpenAI calls, learnability, weekly completion time and API costs have not been established. The guided journey changes being implemented alongside this audit must receive their own checks and browser walkthrough.

Evidence labels used below: **Implemented** means the behavior is present in source; **automated evidence** names relevant tests; **unverified** means the claim still needs direct observation or measurement. A mocked provider or peer connection is not evidence that a real voice session connected.

**Correction status:** The core capabilities in the checklist below were inspected in the existing build. The UX observations are explicitly **pre-correction findings**, not assertions that those defects remain after the current patch. The parent is implementing ordered three-step guidance, explicit already-loaded sample state, shared typed/live overview guidance, duplicate counts covering pending and saved work, and call counts excluding contacted/snoozed episodes. The correction’s final automated checks and the acceptance walkthrough remain separate evidence; this audit does not award a visual or usability pass.

## The three judge checklist items

| Original outcome | Current implementation and evidence | Honest status and remaining proof |
|---|---|---|

In the demo, show the three source identities becoming one, verify the complete history, then undo. Verify the review and Undo controls in a browser. |
| Staff receive a weekly list of late regular donors with last gift, usual amount/timing and a suggested note | `src/lib/patterns.ts` infers monthly, quarterly and annual cadence, excludes purchases, computes usual amounts and supplies expected dates and days late. The follow-up screen displays the facts and an editable/copyable draft. Contact statuses, snooze and undo are persisted; `src/lib/outreach.ts` distinguishes a completed episode from a future lapse. `tests/patterns.test.ts`, `tests/outreach.test.ts`, `tests/commands.test.ts` and storage tests cover those rules. | **Implemented with automated evidence; staff usability unverified.** Elena Ruiz’s December 2025 lapse must appear explicitly in the demo. Factual templates work offline; the optional SDK Note Writer has not been run live here. |
| A failed monthly gift is noticed within days | Miguel Santos has a $75 monthly pattern ending October 2, 2026; the next expected gift is November 2 and becomes late on November 7. Tests verify the five-day boundary, month-end clamping, future dates and one-time-gift interference. The wording identifies a missing monthly gift and treats a card problem as only one possible explanation. | **Missing-gift detection is implemented and tested. Demonstrate the five-day rule on current sample records; do not claim processor monitoring. |

The original problem combines two different guarantees. GiftGuard can calculate a missing-gift signal five days after a known expected date. It cannot verify a failed card or discover new facts while no new files are supplied. The interface and pitch should retain that distinction.

## Pre-correction findings for Denise’s journey

These findings describe the source inspected **before the guided-journey correction**. They explain why the correction is needed. Do not carry them forward as unresolved implementation defects without rechecking the completed patch. The acceptance checks below determine whether the changes resolve the issues for Denise.

1. **Make the first useful action obvious.** The sample starts with 899 transactions, pending duplicate groups and nine follow-up suggestions. A primary instruction to upload first conflicts with that prepared state. Say that sample files are already loaded and offer the next pending step. In a genuinely empty workspace, make uploading the first action. Never label the seeded 899 as this week’s new gifts.
2. **Use the task names, with actual outstanding counts.** “Review” and “Follow-up” require interpretation. Prefer “Review duplicates” and “Calls this week.” Show pending and deferred duplicate work accurately; a combined review badge is appropriate when that breakdown is visible. Count calls with `needsOutreach`. A contact update, snooze, merge or undo should refresh the same counts everywhere. Call badges must not count completed or currently snoozed work.
3. **Show a three-step routine, not three unexplained metrics.** Each step should show what is ready, what needs attention and one clear next action. The sample should explain why upload is already complete; a real upload should lead directly to duplicate review or calls. The assistant remains an optional way to perform the same work.
4. **Do not hide deferred decisions behind a success state.** Skipped groups are accessible through “Include saved for later,” but a zero-pending state can still say “All reviewed.” Distinguish “No pending groups” from “N saved for later,” keep the deferred count visible, and offer a direct way back to them.
5. **Put the means of contacting someone beside the note.** The inspected follow-up card shows phone but requires opening donor history to find email. Show available email and phone beside the draft/outcome controls, with plain missing-contact text. Keep the staff-led copy/contact flow; automatic sending is unnecessary.
6. **Finish each step with a next action.** The review screen already links toward follow-up, but wording and the final call-list state need to complete the weekly routine. After review, offer the actual number of remaining calls. After outreach, show that outstanding work is complete, preserve access to contacted/deferred records and Undo, and explain that the next review starts with current exports.
7. **Protect the demo from overclaims.** Restore Elena in the demo, distinguish missing gifts from failed payments, label template versus AI drafts, and rehearse real SDK and live-voice paths. These matter more to the original judging checklist than additional animation.

## Acceptance journey

Run this with a person who has not seen the implementation. Observe hesitation and wrong turns; do not coach them through hidden controls. The under-five-minute learning and under-ten-minute weekly targets are measured only after such a session. Define the ten-minute target as preparing the weekly work: uploading, reviewing likely duplicates and preparing the call list/drafts. Track actual conversations and personal email work separately; do not imply that Denise can complete nine real calls in ten minutes.

| Step | What Denise should understand and do | Acceptance evidence |
|---|---|---|
| Enter the sample | “These are made-up records, already loaded. Here is my next step.” | Sample state is explicit. History totals are distinct from newly uploaded counts. One primary next-step action leads to the pending work. |
| Enter an empty real workspace | “I need the four downloaded files.” | Upload is the primary action; missing sources are named. No seeded numbers appear as real data. |
| Upload and resolve an unfamiliar heading | Drop files, answer only the specific unresolved question, continue. | Inline clarification preserves the selected files. Valid rows are counted honestly, rejected/conflicting rows are explained, and replay adds no new transactions. A useful next-step action remains visible. |
| Review Rosa | Read why three records may belong together, inspect conflicts and choose contact details if necessary. | No data changes before the exact confirmation. After confirming, one donor has all three original transactions. Undo restores the prior links and totals. Counts update. |
| Defer a doubtful pair | Save the group for later without losing it. | Pending and deferred work are distinguished. The deferred group remains reachable after navigation and subsequent actions. The interface does not claim it was resolved. |
| Understand the call list | Find Elena, Miguel and a quarterly donor; explain why each appears. | Last gift date/amount, usual cadence/amount, expected date and lateness are visible. December 2025 is identified correctly; December 2026 is not prematurely called late. Miguel is five days late on the fixed demo date. |
| Prepare an actual follow-up | Read the note against the facts, choose the appropriate language, copy it and find contact details. | Note and contact information are available in the same work area. Template/AI status is honest. The app does not claim that copying sent a message. |
| Record the outcome | Mark Called/Emailed/Left message or snooze; optionally add a result. | The exact change is reviewed, saved and reflected in outstanding counts. Undo works. Snooze expires on its reminder date; a later missed-gift episode can return. |
| Finish | Know that this week’s outstanding work is handled and what to do next week. | Completion is based on outstanding tasks, not a fixed success banner. Deferred/contacted items remain discoverable. The next upload is the clear future step. |
| Use voice optionally | Connect once, ask for a donor, ask a follow-up, interrupt, request a draft, then propose a change. | Real two-way audio stays connected. Grounded results appear in the workspace. The microphone pauses for the on-screen approval; saying yes alone changes nothing. End/close releases the microphone and audio. A typed/button fallback remains usable. This requires a real browser/network test. |

## A three-minute judging sequence

Use the exact current sample counts shown by the app. The original PRD’s illustrative “142 new gifts” is not the current seed and must not be recited as an observed import result.

| Time | Demonstration | Evidence delivered |
|---|---|---|
| 0:00–0:15 | “Denise needs one donor list and a short list of people to contact. These are made-up records already loaded from four sources.” Point to the three-step routine. | Problem, user and prepared sample state are clear. |
| 0:15–0:35 | Show the four sources. If time permits, re-upload a supplied sample and show no new transactions; describe this accurately as replay protection. | Spreadsheet compatibility and safe repeat imports. Do not imply this is an empty-workspace first import. |
| 0:35–1:20 | Review Rosa’s three identities, read the reason, confirm, open the combined history, undo and show preserved totals. | Human decision, one donor, provenance, all transactions kept, reversibility. |
| 1:20–1:55 | Open calls. Show Elena’s missed December 2025 gift, then Miguel’s expected November 2 monthly gift, five days late on November 7. Briefly show quarterly support if it fits. | Both longstanding lapse detection and the five-day monthly signal. Say “missing monthly gift,” not “confirmed failed card.” |
| 1:55–2:25 | Show the facts beside a note, copy it and record a call. The outstanding count falls. | A usable weekly action, not just an alert. No automatic sending is claimed. |
| 2:25–2:50 | If rehearsed successfully, start or continue live voice: ask who still needs a call, then request a specific duplicate review or draft. Show that a proposed change still needs the on-screen confirmation. | Natural conversation, useful agent work and the human approval boundary. Use typed controls if live voice is unavailable and disclose the fallback. |
| 2:50–3:00 | Close with the achieved behaviors and the stack actually demonstrated. | “One reviewed donor identity, every transaction preserved, and timely follow-up suggestions from the latest exports.” Time saved, money recovered and API cost remain goals until measured. |

Before submission, install and run the real required SDK, complete the unrestricted browser/audio rehearsal, verify the three named cases, and time the sequence. If any live element remains unverified, report that limit rather than presenting test doubles or templates as a live agent demonstration.
